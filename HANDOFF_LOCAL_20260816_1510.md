## One Bridge, Many Client Extensions

Final architecture decision:

- Use one shared Local Collector bridge/app per machine.
- Use one unpacked Chrome extension folder per client.
- Each client extension is loaded into the Chrome profile/account for that client.
- All extensions talk to the same bridge.
- The bridge routes jobs and output by client identity and extension identity.

Canonical layout:

```text
{agency_root}/
  solo-agency-local-collector/         # bridge runtime only
  extensions/
    {client_slug}/                     # Chrome Load unpacked folder per client
  daily-content-pipeline/              # data/config/output only
```

Each per-client extension folder must contain `client_binding.json` with:

- `client_slug`
- `client_name`
- `extension_instance_id`
- `extension_display_name`

Extension display name must put client name first, for Chrome truncation:

```text
{Client Name} - Solo Agency Collector
```

Examples:

- `AvenNgo - Solo Agency Collector`
- `Angela Do - Solo Agency Collector`

Bridge responsibilities:

- know which client each extension belongs to;
- expose/record extension health;
- route private data source jobs to the right extension instance;
- write collector output only under that client's folder;
- write status/log files that agents can read from sandbox when localhost is unreachable;
- know which agent/session is operating which client;
- never mix client A data with client B data.

## Collector Job Model

Old risk: a single `run_now_request.json` can be overwritten when multiple clients are requested at once. This is especially dangerous if an agent forgets to enqueue the second client.

Chosen direction: parallel per-client jobs.

Target model:

```text
daily-content-pipeline/collector/jobs/pending/{client_slug}-{run_id}.json
```

Rules:

- Different clients can have jobs pending/running at the same time.
- Jobs are claimed by matching `client_slug + extension_instance_id`.
- Jobs for the same client/profile remain sequential until complete or TTL expires.
- Output path must be:

```text
daily-content-pipeline/collector/inbox/YYYY-MM/{client_slug}/{run_id}/
```

Automation should write one unique job file per client when localhost API is unavailable but file-based collector health indicates the correct bridge/extension is available.

## Chrome Background Limitation And Current UX Decision

Observed issue: Chrome tabs opened by the extension may not fully load/scroll in background. Collection often starts only when the tab is activated/focused. This likely existed in the old 1-1 model too, but earlier testing may have accidentally focused the tab.

Current practical workaround:

- activate the tab during scan;
- show a clear top-right collector overlay;
- overlay indicates data is being captured under user approval;
- overlay says no username/password/cookie is sent out;
- show a compact scrolling list of collected items so user sees progress;
- close tab after scan.

This is safer and more transparent than trying to silently collect in a throttled background tab.

## Public/Private Report Separation

Final report decision: one canonical report set per client/day/run, made of three HTML files:

```text
{client-name}-public-data-sources-report.html
{client-name}-private-data-sources-report.html
{client-name}-daily-report.html
```

Rules:

- The public lane report is full and complete for public data sources only.
- The private lane report is full and complete for private data sources only.
- Both lane reports have the same report structure: source coverage, evidence, Lead & Competitor Opportunities, idea matrix, best idea, draft/recommendation, blockers.
- Private lane often runs after public lane. When private finishes later, update only the private lane report and daily report index. Do not overwrite public lane report.
- The daily report is a concise index/status page that links to both lanes and shows blockers, notifications, and next action.
- Latest human-facing link should normally point to `{client-name}-daily-report.html`.
- Two notifications are acceptable: `public_report_ready` and `private_report_ready` / `private_report_blocked`.

State file:

```text
outputs/YYYY-MM/YYYY-MM-DD/{client-name}-report_state.json
```

Use this so later passes update only the intended lane.
